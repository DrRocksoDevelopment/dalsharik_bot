# Дальшарик — OPENCODE.md

## 0. Проект

**Рабочее название:** Дальшарик

Дальшарик — Telegram-бот для групповой викторины.

Основная игровая механика:

> Бот публикует событие и предлагает игрокам предсказать, что произошло дальше.

Игроки отвечают в течение заданного времени.

После окончания периода ответов бот публикует результаты:

- сколько участников ответило;
- сколько правильных и неправильных ответов;
- процент правильных ответов;
- время реакции каждого участника;
- самый быстрый правильный ответ;
- распределение вариантов ответов;
- начисленные очки;
- текущие серии игроков;
- краткое объяснение правильного ответа;
- следующий игровой вопрос.

Дальшарик — НЕ обычная викторина на знание фактов.

Главная игровая эмоция:

> «Я знаю, что произошло. Но что было дальше?»

---

# 1. Главный принцип

Игровой цикл:

```text
EVENT
  ↓
QUESTION
  ↓
TELEGRAM QUIZ
  ↓
PLAYERS ANSWER
  ↓
WAIT
  ↓
CLOSE POLL
  ↓
CALCULATE RESULTS
  ↓
PUBLISH RESULTS
  ↓
EXPLAIN WHAT REALLY HAPPENED
  ↓
NEXT EVENT
```

Для MVP основной режим — **групповой**.

Не проектировать MVP вокруг личных чатов.

---

# 2. Группа является игровой сессией

Каждый Telegram chat/group имеет собственную конфигурацию.

Конфигурация должна включать как минимум:

```text
enabled
answer_window
question_types
categories
difficulty_range
question_interval
```

Пример:

```json
{
  "chatId": "-100123456",
  "enabled": true,
  "answerWindow": 3600,
  "questionInterval": 7200,
  "questionTypes": [
    "history",
    "science",
    "technology"
  ],
  "difficultyMin": 1,
  "difficultyMax": 5
}
```

Конфигурация хранится отдельно для каждого чата.

---

# 3. Время ответа

После публикации вопроса начинается окно ответов.

По умолчанию:

```text
1 час
```

Значение должно быть конфигурируемым индивидуально для каждого чата.

После окончания периода:

1. poll закрывается;
2. фиксируются результаты;
3. рассчитывается статистика;
4. публикуется итоговое сообщение.

Не публиковать правильный ответ до окончания окна.

---

# 4. Telegram Poll

Использовать нативный Telegram quiz poll.

Стек:

- Node.js
- TypeScript
- Telegraf
- Telegram Bot API

Для каждого опубликованного poll сохранять связь:

```text
telegramPollId
chatId
questionId
messageId
createdAt
expiresAt
```

Poll должен быть однозначно сопоставлен с вопросом.

---

# 5. Ответ пользователя

Для каждого ответа фиксировать:

```text
userId
chatId
questionId
telegramPollId
selectedOption
isCorrect
answeredAt
reactionTime
points
```

`reactionTime`:

```text
answeredAt - pollCreatedAt
```

Время хранить с достаточной точностью, чтобы корректно определять самые быстрые ответы.

Для отображения использовать удобный формат:

```text
4.2 сек
17 сек
2 мин 14 сек
```

---

# 6. Итоги вопроса

После окончания окна ответов бот публикует отдельное итоговое сообщение.

Пример:

```text
🏁 Итоги

Ответили: 17

✅ Правильно: 11
❌ Неверно: 6

Точность: 64.7%

⚡ Самый быстрый правильный ответ:
@username — 3.8 сек

🐢 Самый поздний правильный:
@username — 48 мин 12 сек

Варианты:
🅰️ 3
🅱️ 2
🅲 11
🅳 1
```

После статистики:

```text
📖 А на самом деле...

[краткое объяснение правильного ответа]
```

Текст объяснения генерируется ИИ на этапе подготовки вопроса и хранится вместе с вопросом.

---

# 7. Порядок публикации результата

Итоговое сообщение должно иметь логическую структуру:

1. заголовок;
2. количество участников;
3. правильные / неправильные;
4. процент правильных;
5. время реакции;
6. статистика вариантов;
7. очки;
8. краткое объяснение;
9. источник/источники;
10. игровой слоган.

Не перегружать сообщение.

---

# 8. Очки

Очки зависят от двух факторов:

1. сложности вопроса;
2. серии правильных ответов пользователя.

Базовые очки определяются сложностью.

Пример:

```text
difficulty 1 → 1 point
difficulty 2 → 2 points
difficulty 3 → 3 points
difficulty 4 → 4 points
difficulty 5 → 5 points
```

Конкретная шкала должна быть вынесена в конфигурацию/константы.

---

# 9. Бонус за серию

Серия правильных ответов увеличивает коэффициент начисления очков.

Максимальный коэффициент:

```text
×2.00
```

Конкретная функция должна быть конфигурируемой.

После неправильного ответа коэффициент сбрасывается:

```text
streak = 0
multiplier = 1.0
```

Механика серии реализуется уже в MVP.

Формулу вынести в отдельный модуль, например:

```ts
calculateStreakMultiplier(streak: number): number
```

Не зашивать формулу непосредственно в обработчик Telegram poll.

---

# 10. Очки за уже решённый вопрос

Очень важное правило.

Пользователь может встретить тот же вопрос в другом чате.

Если пользователь **уже отвечал на этот вопрос ранее**, повторный ответ:

- допускается;
- отображается в статистике текущего чата;
- НЕ начисляет очков.

Уникальность определяется глобально:

```text
userId + questionId
```

Если такая комбинация уже существует:

```text
points = 0
```

Повторный ответ не должен позволять искусственно фармить очки или серию.

---

# 11. Серии

Серия — свойство пользователя.

В MVP:

```text
currentStreak
bestStreak
streakMultiplier
```

Серия увеличивается после правильного ответа.

После неправильного:

```text
currentStreak = 0
```

Если вопрос повторный и пользователь отвечает на него снова:

**не изменять серию**.

В будущем предусмотреть:

- ежедневную серию;
- серию внутри категории;
- серию без ошибок;
- серию в конкретном чате;
- специальные достижения.

Но в MVP реализовать только базовую серию.

---

# 12. Типы вопросов

Типы вопросов должны конфигурироваться **для каждого чата отдельно**.

Пример:

```json
{
  "questionTypes": [
    "historical_next_event",
    "scientific_next_event",
    "technology_next_event"
  ]
}
```

Другой чат:

```json
{
  "questionTypes": [
    "historical_next_event",
    "culture_next_event"
  ]
}
```

Не привязывать тип вопроса глобально к боту.

---

# 13. Базовый тип MVP

Основной тип:

```text
historical_next_event
```

Механика:

```text
EVENT A
   ↓
What happened next?
   ↓
A / B / C / D
```

В будущем предусмотреть:

```text
scientific_next_event
technology_next_event
business_next_event
culture_next_event
geography_next_event
```

Архитектура должна позволять добавлять типы без переписывания quiz engine.

```json
      "id": "B",
```

# 15. Генерация вопросов

Тексты вопросов, варианты ответов и объяснения должны прорабатываться с помощью ИИ.

Pipeline:

```text
SOURCE EVENT
    ↓
AI
    ↓
question
answers
correct answer
explanation
    ↓
validation
    ↓
question repository
    ↓
production
```

LLM используется для редакторской работы, а не как единственный источник фактов.

Фактическая информация должна быть проверяема по источникам.

---

# 16. Генерация неправильных вариантов

Неправильные варианты должны быть:

- правдоподобными;
- относящимися к тому же контексту;
- примерно сопоставимыми по длине;
- не содержащими очевидного абсурда;
- не выдающими правильный ответ стилистически.

Если игрок может угадать ответ только по форме вариантов — вопрос плохой.

---

# 17. Сложность

Каждый вопрос имеет difficulty:

```text
1 — очень легко
2 — легко
3 — средне
4 — сложно
5 — очень сложно
```

Сложность должна влиять на:

- базовые очки;
- подбор вопросов;
- статистику;
- потенциально будущую адаптацию.

---

# 18. Выбор вопросов

Для каждого чата выбор производится с учётом:

1. разрешённых типов;
2. разрешённых категорий;
3. допустимой сложности;
4. вопросов, уже использованных в этом чате;
5. вопросов, которые игроки уже видели;
6. случайности;
7. возможных связей между событиями.

На уровне MVP:

```text
eligible questions
    ↓
filter by chat config
    ↓
filter recently used
    ↓
random weighted selection
```

---

# 19. Вопрос не должен повторяться в чате

После публикации вопрос считается использованным в конкретном чате.

Хранить:

```text
chatId
questionId
publishedAt
```

Не публиковать один и тот же вопрос повторно в том же чате, если не предусмотрен специальный режим повторения.

---

# 20. Глобальная история вопросов

Необходимо хранить глобальную историю ответов пользователей.

Это позволяет определить:

> пользователь уже отвечал на этот вопрос или нет.

Это важно даже если ответ был сделан в другом Telegram-чате.

---

# 21. Хранилище

Вместо SQLite использовать JSON-файлы.

Не писать произвольные `fs.writeFile()` по всему проекту.

Создать абстракцию хранилища.

Например:

```text
src/storage/
    storage.ts
    json-storage.ts
    lock.ts
```

Интерфейс:

```ts
interface Storage<T> {
  get(id: string): Promise<T | null>
  getAll(): Promise<T[]>
  find(predicate): Promise<T[]>
  insert(item: T): Promise<void>
  update(id: string, patch: Partial<T>): Promise<void>
  delete(id: string): Promise<void>
}
```

Конкретная реализация:

```text
JsonStorage
```

---

# 22. Блокировки JSON

Так как бот может одновременно получать несколько Telegram updates и выполнять scheduler, JSON-файлы нельзя считать автоматически безопасными.

Необходима простая система блокировок.

Например:

```text
data/
    users.json
    questions.json
    answers.json
    chats.json
    polls.json
    stats.json

    locks/
        users.lock
        answers.lock
```

Механизм должен предотвращать race condition при:

```text
read
modify
write
```

Предпочтительно реализовать атомарную запись через:

```text
temporary file
    ↓
fsync
    ↓
rename
```

и отдельную очередь/lock на файл.

Не делать сложную распределённую систему блокировок.

Бот работает как один процесс.

# 25. Logging

Использовать Winston.

Должны существовать как минимум:

```text
console transport
file transport

```

Конфигурация:


Логирующий Telegram transport должен:

# 27. Scheduler

Scheduler работает внутри Node.js процесса.

Для каждого активного чата:

```text
check chat schedule
    ↓
is it time?
    ↓
select question
    ↓
publish poll
    ↓
schedule expiration
```

После expiration:

```text
close poll
    ↓
collect results
    ↓
calculate points
    ↓
update statistics
    ↓
publish summary
```

После этого scheduler ждёт следующего интервала.

---

# 28. Надёжность scheduler

После перезапуска процесса бот должен восстановить состояние.

Например:

```text
polls.json
```

содержит:

```text
pollId
chatId
questionId
createdAt
expiresAt
status
```

При старте:

1. найти активные polls;
2. определить истёкшие;
3. завершить их;
4. восстановить таймеры для остальных.

Нельзя полагаться только на `setTimeout`.

---

# 29. Обработка повторных Telegram updates

Обработчики должны быть идемпотентными.

Telegram update может быть обработан повторно.

Не должно происходить:

```text
+5 points
+5 points
```

из-за повторной обработки одного update.

Для этого хранить идентификаторы обработанных событий или проверять уникальность ответа.

---

# 30. Система очков

Расчёт вынести в отдельный модуль:

```text
src/game/scoring.ts
```

API примерно:

```ts
calculatePoints({
  difficulty,
  streak,
  alreadyAnswered
})
```

Результат:

```ts
{
  basePoints,
  multiplier,
  points,
  isRepeat
}
```

Пример:

```text
difficulty = 4
base = 4

streak multiplier = 1.5

points = 6
```

При повторном вопросе:

```text
points = 0
```

но:

```text
isRepeat = true
```

---

# 31. Время реакции

Время реакции считается от момента публикации вопроса до момента ответа.

Не использовать время окончания poll.

Хранить точное значение.

Это позволяет определить:

- самый быстрый правильный ответ;
- среднее время;
- медиану;
- распределение времени;
- скорость конкретного игрока.

---

# 32. Рейтинг в группе

После завершения вопроса можно показывать:

```text
🏆 За этот вопрос

@user +8
@user +6
@user +4
```

В MVP достаточно:

- top 3;
- лучший результат;
- fastest correct;
- текущая серия.

---

# 33. Игровые слоганы

Слоган НЕ является постоянной строкой.

Это часть игровой механики.

Каждое завершение вопроса может выбирать случайный слоган из набора.

Примеры:

```text
«Ну и кто бы мог подумать?»
«История решила иначе.»
«А вот и поворот.»
«Ты почти угадал.»
«История не согласна.»
«Вот что было дальше.»
«А ты ставил не туда.»
«Неплохо. Но нет.»
«История нанесла ответный удар.»
```

Система должна позволять иметь разные наборы:

```text
correct
wrong
close
hard
easy
fast
many_players
few_players
```

Например:

```ts
getGameSlogan(context)
```

Слоганы должны быть конфигурируемыми и расширяемыми без изменения игровой логики.

# 36. Будущие расширения серий

- ежедневные streaks;

# 37. Будущие цепочки событий

События могут быть связаны:

```text
EVENT A
 ↓
EVENT B
 ↓
EVENT C
```

Это особенно важно для будущей механики.

Например:

```text
Question:
"What happened next?"

Correct:
EVENT B

Next question:
"What happened next?"
```

Таким образом пользователь может пройти историческую цепочку.

В MVP достаточно предусмотреть:

```text
nextEventId
```

или отдельную relation table.

Не реализовывать полноценный graph engine.

---

# 38. Будущая альтернативная история

```text
Reality
    ↓
A
    ↓
B
    ↓
C

Alternative
    ↓

    ↓

```

Это потенциально отдельный игровой режим.

Не реализовывать в MVP.

# 39. Данные вопросов

Первоначально создать качественный seed dataset.

Минимум:

```text
100 questions
```

Распределение:

```text
history
science
technology
culture
geography
```

Количество вопросов не должно быть самоцелью.

Качество важнее количества.

# 40. Проверка вопросов

Каждый вопрос перед публикацией должен пройти:

1. проверку существования события;
2. проверку правильного ответа;
3. проверку источника;
4. проверку однозначности;
5. проверку вариантов;
6. проверку сложности.

LLM может выполнять предварительную редактуру.

Финальные данные должны быть валидируемыми.

# 41. Тестирование

Обязательно протестировать:

### Game

- публикацию вопроса;
- завершение вопроса;
- правильный ответ;
- неправильный ответ;
- отсутствие ответа;
- несколько игроков;
- повторный ответ;
- ответ пользователя, уже решавшего вопрос в другом чате.

### Scoring

- difficulty;
- streak;
- multiplier;
- multiplier cap;
- reset after wrong answer;
- zero points for repeat.

### Scheduler

- создание poll;
- expiration;
- restart;
- восстановление после перезапуска.

### Storage

- concurrent writes;
- lock;
- atomic write;
- corrupted JSON;
- recovery.

### Telegram

- duplicate update;
- unknown poll;
- deleted chat;
- bot removed from chat.

# 43. Правило для OpenCode

Не добавлять технологии и инфраструктуру только потому, что они являются распространённым стандартом.

Не использовать:

- Express;
- SQLite;
- PostgreSQL;
- Redis;
- Docker;
- Kubernetes;
- отдельные микросервисы;

если текущая задача не требует их непосредственно.

Архитектура должна оставаться максимально простой:

```text
Telegram
   ↓
Telegraf
   ↓
Game Engine
   ├── Question Engine
   ├── Scoring
   ├── Statistics
   ├── Scheduler
   └── Content
         ↓
      JSON Storage
```

# 45. Главный KPI

Главный KPI проекта:

> **Хочет ли человек ответить на следующий вопрос?**

Не:

- количество таблиц;
- количество команд;
- количество API;
- количество категорий;
- количество AI-вызовов.

Хороший Дальшарик должен создавать ощущение:

> «Блядь, интересно, а что было дальше?»
