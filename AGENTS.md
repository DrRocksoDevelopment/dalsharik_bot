# AGENTS.md — правила проекта «Дальшарик»

## Коммиты

Формат: `<prefix>: <описание на русском>`

- Префикс — английский, из списка Conventional Commits:
  - `feat:` — новая функциональность
  - `fix:` — исправление бага
  - `refactor:` — рефакторинг без изменения поведения
  - `docs:` — документация
  - `test:` — тесты
  - `chore:` — служебные изменения (сборка, конфиги, деплой)
  - `perf:` — оптимизация производительности
- Описание — краткое, на русском языке.
- Каждый коммит должен быть атомарным: одна логическая правка — один коммит.
- Перед коммитом: `npm run build` и `npm test` должны проходить.

## Внешние библиотеки

- При работе с внешними библиотеками используй Context7 для проверки актуальной документации и API, когда важно версионно-специфичное поведение.

## Модель веток (Git Flow)

- `main` — стабильная ветка, только релизы.
- `develop` — ветка интеграции, куда сливаются готовые фичи.
- `feature/<name>` — ветки новых функций, от `develop`.
- `hotfix/<name>` — срочные исправления, от `main`.
- `release/<version>` — подготовка релиза, от `develop`; после релиза мержится в `main` и `develop`.

Рабочий цикл:

1. От `develop` создаётся `feature/<name>`.
2. По завершении фича мержится в `develop`.
3. Когда `develop` готова к релизу — создаётся `release/<version>`.
4. Релиз тагается `v<version>` и мержится в `main` и `develop`.

## Трекинг задач: issues и доска проекта

- Репозиторий `DrRocksoDevelopment/dalsharik_bot`, все задачи, баги и идеи — GitHub Issues.
- Доска проекта (Projects v2, project №5): каждая issue добавляется на доску с полями **Status** (`Backlog` → `Ready` → `In Progress` → `In Review` → `Done`) и **Priority** (`P0`/`P1`/`P2`).
- `gh` недоступен в PATH внутри npm-скриптов: перед командами `gh` подставлять `$env:PATH = "C:\Program Files\GitHub CLI;$env:PATH"`.

Поддержание актуального состояния (обязательно, не забывать):

- Любую новую идею, баг или нововведение сразу фиксировать: создать issue (если ещё нет) → добавить на доску со статусом и приоритетом. Даже нереализованные идеи сохранять как issue (например, `question:` или «перспектива»).
- Каждая функциональная правка: запись в `CHANGELOG.md` (`[Unreleased]`) + ссылка на связанный issue.
- По завершении задачи: `gh issue close` с комментарием-подтверждением приёмки (чеклист из issue), статус на доске → **Done**.
- После релиза: ченджелог, тег `v<version>`, GitHub-релиз, мердж в `main`/`develop`, синхронизация доски (выполненные → `Done`, незакрытые → актуальный статус).

## Релизы

- Версия — семантическое версионирование (major.minor.patch).
- `CHANGELOG.md` — Keep a Changelog. При каждой функциональной правке запись в `## [Unreleased]`; перед релизом перенести её в `## [v<version>] — <дата>` и закоммитить.
- Скрипты:
  - `npm run release:patch|minor|major` — сборка, тесты, проверка секции новой версии в `CHANGELOG.md` (без неё релиз не пройдёт), bump версии, коммит и тег `v<version>`.
  - `npm run release:push` — пуш `main`, `develop` и тегов в origin, автосоздание GitHub-релиза из секции ченджелога (`gh release create|edit`).
- Для MVP допускается релиз напрямую из `main` через `release:patch`.
